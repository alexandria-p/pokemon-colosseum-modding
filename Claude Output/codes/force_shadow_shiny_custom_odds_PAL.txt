-------------------------------------------------------------------------------
WHAT CHANGED FROM THE US BUILD
-------------------------------------------------------------------------------
Exactly two words, plus the C2 address:

    hook    US 0x801FA3E8  ->  PAL 0x801FEC94     (C21FA3E8 -> C21FEC94)
    global  US 0x8047ADB8  ->  PAL 0x804C8268
              3D608047 -> 3D60804C   (lis r11, 0x8047 -> lis r11, 0x804C)
              616BADB8 -> 616B8268   (ori 0xADB8      -> ori 0x8268)

Every other word is byte-identical, and the line count and all four branch
offsets are unchanged.

That is because nothing else in this code refers to an address: `mftb` reads a
CPU register, the decimal decode is pure arithmetic, and the modulo is
`divwu`/`mullw`/`subf`.  Only the save-base pointer is region-specific.


-------------------------------------------------------------------------------
HOW THE DECIMAL FIELD WORKS
-------------------------------------------------------------------------------
Gecko codes are hex, so a naive "put your number here" field would read 0512 as
0x512 = 1298 and quietly give you the wrong odds -- a mistake you could never
detect by playing.  This code treats the field as four decimal DIGITS:

    li     r0, 0
    ori    r0, r0, 0xXXXX          ; <- your field, four packed digits
    rlwinm r8,  r0, 0,  28, 31     ; ones      = digit 0
    rlwinm r9,  r0, 28, 28, 31     ; tens      = digit 1
    rlwinm r10, r0, 24, 28, 31     ; hundreds  = digit 2
    rlwinm r12, r0, 20, 28, 31     ; thousands = digit 3
    mulli  r9,  r9,  10
    mulli  r10, r10, 100
    mulli  r12, r12, 1000
    add    r12, r12, r10
    add    r12, r12, r9
    add    r12, r12, r8            ; r12 = N

So 0512 really means five hundred and twelve.  A digit above 9 is not rejected,
just misread: 00FF decodes as 15*10 + 15 = 165.  Stick to 0-9.


-------------------------------------------------------------------------------
FULL DISASSEMBLY
-------------------------------------------------------------------------------
    li     r6, 0                ; the overwritten original instruction
    cmplwi r30, 0               ; the game's own is-shadow flag
    beq    done                 ; ordinary Pokemon -> untouched

    li     r0, 0                ; --- decode the decimal field ---
    ori    r0, r0, 0xXXXX       ; <<< YOUR ODDS GO HERE
    rlwinm r8,  r0, 0,  28, 31
    rlwinm r9,  r0, 28, 28, 31
    rlwinm r10, r0, 24, 28, 31
    rlwinm r12, r0, 20, 28, 31
    mulli  r9,  r9,  10
    mulli  r10, r10, 100
    mulli  r12, r12, 1000
    add    r12, r12, r10
    add    r12, r12, r9
    add    r12, r12, r8         ; r12 = N
    cmplwi r12, 0
    beq    done                 ; N = 0000 -> never fire, and no divide by zero

    mftb   r11                  ; --- roll: is TB divisible by N? ---
    divwu  r0, r11, r12
    mullw  r0, r0, r12
    subf   r0, r0, r11          ; r0 = TB mod N
    cmplwi r0, 0
    bne    done                 ; N-1 outcomes in N -> leave it alone

    lis    r11, 0x804C          ; --- fire ---
    ori    r11, r11, 0x8268     ; r11 = &saveBasePtr  (PAL 0x804C8268)
    lwz    r11, 0(r11)
    cmplwi r11, 0
    beq    done                 ; no save loaded -> untouched
    lwz    r7, 0x9C(r11)        ; player's (SID << 16) | TID
    rotlwi r7, r7, 16           ; -> (TID << 16) | SID
    li     r6, 1                ; force shiny
  done:
    nop                         ; branch target (0x801FED10)

32 instructions = 16 lines.  All four branches are PC-relative within the block
and land on the trailing nop, so the line count and offsets never change no
matter what you put in the field.

Registers: r0, r8, r9, r10, r11, r12 are volatile and dead at this hook.
r3/r4/r5 hold the PID generator's other arguments and are not touched; r7 is
overwritten only on the firing path.


-------------------------------------------------------------------------------
HOW TO TEST IT AT BATTLE START (PAL)
-------------------------------------------------------------------------------
The PID is rolled during battle SETUP, before anything is sent onto the field,
so you can see the result the moment the battle begins.

PRIMARY BREAKPOINT -- instruction breakpoint at  0x801FEC98

    801FEC90  mr   r7, r25       ; OT trainer id argument
    801FEC94  li   r6, 0         ; <- the Gecko hook lives HERE.  Do not break on
                                 ;    this address: the C2 has replaced it with
                                 ;    a branch, so you would not see li r6, 0.
    801FEC98  bl   0x80128584    ; <- BREAK HERE (the PAL PID generator)
    801FEC9C  mr   r7, r3        ; <- and here: r3 = the freshly rolled PID

At 0x801FEC98, before it executes:

    r6 = 1   the odds check FIRED -- this shadow is being rolled shiny for you
    r6 = 0   it did not fire -- normal roll
    r7       the trainer ID dword in use.  If it fired this is YOUR
             (TID << 16) | SID; otherwise the NPC trainer's.

Step one instruction to 0x801FEC9C and read r3 -- the new PID.  Check it with

    shiny  if  (TID ^ SID ^ PID_high ^ PID_low) < 8

Your TID/SID: read the word at 0x804C8268 to get the save base, then
saveBase+0x9C is (SID << 16) | TID.

FOR LONG ODDS -- use a CONDITIONAL breakpoint at 0x801FEC98 with the condition

    r6 == 1

so it only halts when the code actually fires.

IF THE BREAKPOINT NEVER FIRES for a shadow you are expecting: that shadow
already has a stored PID and the generator is being skipped.  Confirm with a
breakpoint at 0x801FEC64 (`bl 0x801F2FC4`, the stored-PID fetch) -- if THAT one
hits instead, the PID was locked at an earlier encounter on this save.

These breakpoints apply to every PAL build that hooks 0x801FEC94.


-------------------------------------------------------------------------------
CHOOSING N: AVOID FACTORS OF 2, 3 AND 5
-------------------------------------------------------------------------------
The randomness is the CPU timebase, which ticks at 40.5 MHz -- one tick every
24.7 ns, about 675,000 ticks per NTSC frame and 810,000 per PAL frame.  It is
NOT frame-based; it is roughly forty million times finer than that.

But if you reroll by delaying the encounter a whole number of frames, the
timebase advances by a fixed amount each frame, so the value of TB mod N steps by

    675000 mod N   (NTSC)        810000 mod N   (PAL)

and you can only ever reach N / gcd(ticks_per_frame, N) of the N residues.
675000 = 2^3 * 3^3 * 5^6 and 810000 = 2^4 * 3^4 * 5^4, so any N built from 2s,
3s and 5s reaches badly:

    N        US reach   PAL reach   verdict
    4        1 of 4     1 of 4      whole-frame delays change NOTHING
    8        1 of 8     1 of 8      whole-frame delays change NOTHING
    512      64 of 512  32 of 512   poor
    8192     1024       512         poor
    9999     1111       1111        poor
    8003     ALL 8003   ALL 8003    ideal
    7919     ALL        ALL         ideal
    4999     ALL        ALL         ideal

**Pick an N with no factor of 2, 3 or 5** and every residue becomes reachable by
frame delay, which makes rerolling reliable.  8003 = 53 x 151 is ideal.  So are
7919, 4999, and any odd number not divisible by 3 or 5.

Caveat in the other direction: the roll does not happen at a perfectly
frame-quantised instant -- the game reaches it after a variable amount of setup
work, so there is sub-frame jitter and even a power-of-two N will vary somewhat
in practice.  The table says what you can RELY on, not what will always happen.

None of this affects the odds themselves.  Over many independent encounters
every N gives its stated 1-in-N rate.  It only affects how effectively you can
reroll a single encounter by nudging the timing.


-------------------------------------------------------------------------------
WHAT THE ODDS MEAN IN PRACTICE
-------------------------------------------------------------------------------
There are 48 shadow Pokemon, and each PID is rolled ONCE at your first encounter
and then persisted in the save.  So a playthrough is 48 rolls:

    1 in 4      12 expected shiny shadows      ~100% chance of at least one
    1 in 16      3                             95%
    1 in 64      0.75                          53%
    1 in 128     0.375                         31%
    1 in 512     0.094                          9%
    1 in 1024    0.047                          5%
    1 in 8192    0.006                          1%

Below about 1 in 64 you are more likely than not to finish a playthrough with no
shiny shadow at all.

Because the PID is fixed at first encounter, the code must be enabled BEFORE you
meet each shadow Pokemon.  Changing the field afterwards cannot alter one that
has already been rolled.

VERIFICATION
-------------------------------------------------------------------------------
Against the PAL MRAM dump:
  * 0x801FEC94 holds 38C00000 (li r6, 0) -- the re-emitted instruction
  * lis 0x804C / ori 0x8268 resolves to 0x804C8268
  * PAL save base read 0x804559E0; +0x9C = B9EB7002 (SID B9EB, TID 7002)
  * r30 is written once, at 0x801FE8B0, from is-shadow field 19, and is live
  * all four branch offsets land exactly on the trailing nop (0x801FED10)
  * every encoding round-tripped through a disassembler
  * the breakpoint sites disassemble as expected: 0x801FEC98 = bl 0x80128584
    (the PAL PID generator), 0x801FEC64 = bl 0x801F2FC4 (stored-PID fetch)

The decimal decode and the modulo are unchanged from the US build, where they
were simulated across 0001/0004/0008/0064/0512/1024/8192/9999/0000 and sampled
over 400,000 draws at N = 4, 512 and 9999.

The always-on PAL build this derives from is confirmed working in-game, as is
the shadow-only gate it reuses.  This build is NOT yet tested in-game -- test at
60000001 first (every shadow shiny, same as force_shadow_shiny_PAL), then set
your real odds.  At long odds a test producing no shiny proves nothing.
