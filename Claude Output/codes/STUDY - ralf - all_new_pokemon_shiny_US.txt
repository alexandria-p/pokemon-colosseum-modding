Part 1 — four 32-bit code patches, each forcing a shiny flag to 1:
    80125EB8  li r5,  1
    801285A0  li r27, 1     ; PID generator +0x1C — the r6 shiny arg parked in r27
    8012957C  li r3,  1     ; inside the in-battle shiny check
    8012B440  li r0,  1     ; inside battle_pokemon_get_value_with_id

Part 2 — C2 hook, mid-function at PID-generator-caller +0x46C:
    mr     r7, r25          ; the original overwritten instruction
    lis    r6, 0x8013
    lhz    r6, -0x1EC0(r6)  ; halfword at 0x8012E140 — a game-code fingerprint
    cmplwi r6, 0x547F       ; PAL build guard: top half of an rlwinm r31,r3,...
    bne    +0x10            ; wrong build -> skip, leave r7 = r25
    lis    r6, 0x804D
    lwz    r6, 0x8268(r6)   ; 0x8268 sign-extends negative:
                            ;   0x804D0000 - 0x7D98 = 0x804C8268 = &saveBasePtr
    lwz    r7, 0x9C(r6)     ; r7 = player trainer ID dword (raw, NOT swapped)
    nop                     ; branch target

Note: this hook wants the trainer ID dword raw. The force-shadow-shiny code
hooks a different function and needs the halves swapped (rotlwi r7,r7,16).
Same save field, two different consumers — don't copy one into the other.

The 0x547F guard is why this code fails safe rather than crashing on a
non-PAL build: it never reaches the hardcoded pointer.

  Guard re-targeted: lis r6,0x8013 / lhz r6,0x9F78(r6) reads 0x80129F78.
  (0x80130000 - 0x6088 = 0x80129F78; 0x9F78 sign-extends to -0x6088.)

  Global 0x8047ADB8 as an lis/lwz pair.  lwz's displacement sign-extends, so
  the low halfword 0xADB8 (>= 0x8000) forces lis of high+1 = 0x8048 — the same
  correction the PAL original makes with 804D / 8268 for 0x804C8268.
  (The force-shadow-shiny code uses ori instead, which zero-extends, so there
  the split is a plain 8047 / ADB8.)

--- WHICH WRITE DOES WHAT -----------------------------------------------------
Ralf publishes a toggle variant, "All Pokemon Are Shiny On/Off", that uses only
THREE of the four writes -- 80121D44, 80125408, 801272CC -- and labels it
"GFX only".  So those three are the display-side shiny checks, and

    0412442C 3B600001    (li r27, 1 over the mr r27, r6 in the PID generator)

is the write that actually changes the rolled PID.  If you want genuinely shiny
Pokemon rather than merely shiny-looking ones, that is the line that matters.

This code is published by Ralf as "Shiny Nation" -- identical to the block
above, a third independent confirmation of the conversion.

--- VERIFIED against a US MRAM dump (2026-09-04) -------------------------------
* Guard word: 0x80129F78 reads 547F063E, i.e. rlwinm r31, r3, 0, 24, 31.  The
  halfword is 0x547F, so the cmplwi matches and the guard passes on US.
* Hook site: 0x801FA3E4 reads 7F27CB78 (mr r7, r25) — exactly the instruction
  Part 2 re-emits as its first line.
* The hook really does precede the PID generator call:
      801FA3E4  mr   r7, r25       <-- hook
      801FA3E8  li   r6, 0
      801FA3EC  bl   0x80124410    <-- the PID generator
  Note the li r6,0 at 801FA3E8: setting the shiny flag in r6 from this C2 would
  be wiped immediately.  That is why the flag is forced by the 04 write inside
  the callee at 8012442C instead, and why Part 2 only touches r7.
* The four 04 targets currently hold the boolean-producing instruction each
  patch replaces:
      80121D44  rlwinm r5, r0, 1, 31, 31   -> li r5, 1
      8012442C  mr     r27, r6             -> li r27, 1
      80125408  rlwinm r3, r0, 1, 31, 31   -> li r3, 1
      801272CC  rlwinm r0, r0, 1, 31, 31   -> li r0, 1
  The three rlwinm sites share one idiom (xor / cntlzw / slw / rlwinm) — the
  same shiny test compiled in three places.
* Save-base global 0x8047ADB8 confirmed via savedataBiosSetNowSavedataPtr
  (0x80128E14): stw r3, -0x5A68(r13) with r13 = 0x80480820.
