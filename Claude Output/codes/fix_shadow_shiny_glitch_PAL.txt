Pokémon Colosseum — Fix the shadow shiny glitch: give enemy shadow Pokémon
the PLAYER's OT Trainer ID / Secret ID, so a PID that is shiny against the
player actually DISPLAYS as shiny in battle.

PAL / GC6P01.  Written 2026-09-04.
Converted from codes/fix_shadow_shiny_glitch_US.txt, which is confirmed working.
Designed to run alongside the PAL force-shadow-shiny code.

-------------------------------------------------------------------------------
C212811C 00000007

41820020 3D60804C

818B009C 919A0014
BB410008 00000000

Disassembly:
    cmplwi r26, 0            ; r26 = the Pokemon record being built
    beq    skip              ; null record -> do nothing
    lhz    r12, 0xD8(r26)    ; Shadow Pokemon ID  (0 = not a shadow)
    cmplwi r12, 0
    beq    skip              ; ordinary Pokemon -> leave its OT alone
    lis    r11, 0x804C
    ori    r11, r11, 0x8268  ; r11 = &saveBasePtr   (PAL 0x804C8268)
    lwz    r11, 0(r11)       ; r11 = save base
    cmplwi r11, 0
    beq    skip              ; no save loaded yet -> do nothing
    lwz    r12, 0x9C(r11)    ; player's (SID << 16) | TID
    stw    r12, 0x14(r26)    ; record OT SID (+0x14) and OT TID (+0x16)
  skip:
    lmw    r26, 0x8(r1)      ; the overwritten original instruction
    (00000000 = padding to a whole 8-byte line)

13 instructions + 1 padding word = 7 lines.  All three internal branches are
PC-relative within the block, so they stay correct wherever the codehandler
copies it.  They target 0x8012814C, the re-emitted lmw.


-------------------------------------------------------------------------------
WHAT CHANGED FROM THE US VERSION
-------------------------------------------------------------------------------
Only two things:

    hook    US 0x80123FA8   ->   PAL 0x8012811C
    global  US 0x8047ADB8   ->   PAL 0x804C8268
              (lis 0x8047 / ori 0xADB8  ->  lis 0x804C / ori 0x8268)

Everything else is byte-identical.  ori zero-extends, so the global splits
straight down the middle in both regions with no sign-extension correction.

The record offsets used -- +0xD8 (Shadow Pokemon ID), +0x14 (OT SID / OT TID)
and +0x9C (the player's ID dword in the save) -- are save-relative and
IDENTICAL across regions.  The two WiiRD v1.01 tables differ only in the base
pointer, the in-battle absolute addresses and the button activator.


-------------------------------------------------------------------------------
VERIFIED AGAINST THE PAL MRAM DUMP
-------------------------------------------------------------------------------
The PAL OT-setter function at 0x80128064 is instruction-for-instruction
identical to the US one at 0x80123EF0, apart from bl targets:

    80128064  stwu r1, -0x20(r1)
    80128070  stmw r26, 0x8(r1)
    80128074  mr.  r26, r3        ; r26 = record pointer
    8012808C  beq  0x8012811C     ; null record -> straight to the exit
              ... field 113, 114, 115, 116, 117 (OT TID), 118 (OT name) ...
    8012811C  lmw  r26, 0x8(r1)   ; <- HOOK.  r26 still holds the record.
    8012812C  blr

Checks that passed:
  * 0x8012811C holds BB410008 (lmw r26, 0x8(r1)) -- the re-emitted instruction
  * r26 is the record pointer and is not reloaded until that instruction
  * lis 0x804C / ori 0x8268 resolves to 0x804C8268
  * all three branch offsets land exactly on the re-emitted lmw
  * the shadow gate discriminates in the PAL dump's opponent array A:
        Duskull  +0xD8 = 0000
        Spinarak +0xD8 = 0000
        Makuhita +0xD8 = 0001
  * every instruction encoding round-tripped through a disassembler

Address translation confidence (Claude Assets/tools/map_convert.py):
    US 80123FA8 -> PAL 8012811C, inside a 95-function exact-size run.


-------------------------------------------------------------------------------
THE PAL DUMP DEMONSTRATES THE GLITCH
-------------------------------------------------------------------------------
The PAL capture happens to contain the exact bug this code fixes.

    shadow Makuhita, PID F4893D62
    owner  Trudly  (TID DBB7, SID E829):  xor = FA75  -> not shiny
    player Rex     (TID 7002, SID B9EB):  xor = 0002  -> SHINY

The PID is genuinely shiny against the player, but because the record still
carries Trudly's OT (dword at +0x14 = E829DBB7) the game renders it normally.
With this code the record's OT becomes B9EB7002 and it renders shiny.


-------------------------------------------------------------------------------
SCOPE
-------------------------------------------------------------------------------
Gated on the Shadow Pokemon ID, so only shadow Pokemon have their OT rewritten.
The other callers of the OT setter -- the debug-menu path and the e-Card /
bonus gift setups -- are untouched, so those Pokemon keep their distinctive OT
IDs.

Note that a force-shadow-shiny code hooked on the PID generator is itself
unconditional: it forces every rolled PID shiny, not just shadows.  Gating this
code does not narrow that.
