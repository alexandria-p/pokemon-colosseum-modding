Disassembly:
    li     r6, 0             ; the overwritten original instruction
    cmplwi r30, 0            ; r30 = the caller's is-shadow flag
    beq    done              ; ordinary Pokemon -> leave r6=0, r7=r25 untouched
    lis    r11, 0x8047
    ori    r11, r11, 0xADB8  ; r11 = &saveBasePtr  (US 0x8047ADB8)
    lwz    r11, 0(r11)       ; r11 = save base
    cmplwi r11, 0
    beq    done              ; no save loaded -> leave alone
    lwz    r7, 0x9C(r11)     ; player's (SID << 16) | TID
    rotlwi r7, r7, 16        ; -> (TID << 16) | SID, the order this fn wants
    li     r6, 1             ; force shiny
  done:
    nop                      ; branch target

12 instructions = 6 lines exactly.  Both branches are PC-relative within the
block, so they stay correct wherever the codehandler copies it.


-------------------------------------------------------------------------------
WHY THE HOOK MOVED
-------------------------------------------------------------------------------
v1 hooked the PID generator itself (0x80124410), which is shared by every
Pokemon the game rolls -- hence "everything is shiny".

v2 hooks the CALL SITE instead, at 0x801FA3E8 inside
zz_gen_battle_pokemon_from_data_table? (0x801F9F78):

    801FA398  cmplwi r30, 0
    801FA39C  beq    0x801FA3D8      ; not a shadow -> roll a new PID
    801FA3A0  mr     r3, r23
    801FA3A4  bl     0x801EE8F4      ; does this shadow already have a PID?
    801FA3B0  bne    0x801FA3D8      ; no -> roll a new PID
    801FA3B4  bl     0x801EE750      ; YES -> fetch the stored PID
    801FA3D0  bl     set field 111   ; ...and use it
    801FA3D4  b      0x801FA408      ; generator skipped entirely
    801FA3D8  mr     r3, r31
    801FA3DC  mr     r4, r29
    801FA3E0  mr     r5, r28
    801FA3E4  mr     r7, r25         ; OT trainer id argument
    801FA3E8  li     r6, 0           ; <- HOOK.  the shiny-flag argument.
    801FA3EC  bl     0x80124410      ; the PID generator
    801FA408  cmplwi r30, 0          ; r30 tested again to gate shadow setup

r30 is the game's own is-shadow flag: it is loaded once at 0x801FA004 from
pokemon-data field 19 (`rlwinm r30, r3, 0, 24, 31`), is never written again in
this function, and the game itself branches on it at 0x801FA398 and 0x801FA408.
It is live and correct at the hook.

Stars names this same spot in GoD-Tool's Code Snippets CM.swift:
    shinyLockRAMOffset      = 0x801fa3e8   <- our hook
    shadowsOnlyLockRAMOffset = 0x801fa3d8


-------------------------------------------------------------------------------
FIRST ROLL ONLY, AND THE PID PERSISTS
-------------------------------------------------------------------------------
From the branch structure above:

  * FIRST encounter with a given shadow Pokemon -- 0x801EE8F4 reports no stored
    PID, so the generator runs and this code forces the roll shiny against the
    player.  The result is written to field 111 on the record and, when the
    Pokemon is sent onto the field, into the Strategy Memo in the save.

  * EVERY LATER encounter -- 0x801EE8F4 reports a stored PID, so 0x801EE750
    fetches it and `b 0x801FA408` skips the generator completely.  This code
    never runs for that Pokemon again, and does not need to.

0x801EE750 is explicit about where the PID lives:

    lhz   r31, 0xA(r4)      ; entry index, from the shadow table
    bl    0x801EF1E4        ; -> trainer_get_data_pointer(0, 15)
    mulli r4, r31, 12       ; 12-byte stride
    addi  r0, r4, 0x8       ; PID at +0x08
    lwzx  r3, r3, r0

-- the same 12-byte entry / PID-at-+8 layout as the Strategy Memo, and in the
US dump the only copy of Makuhita's PID in save memory is its Strategy Memo
entry.  So the PID is persisted in the save and reused forever after.

Practical consequences:
  * Turning this code off later does NOT undo a shiny PID already rolled.
  * Turning it on later does NOT fix a shadow you have already encountered --
    its PID was fixed at that first encounter.  You need it enabled BEFORE the
    first encounter with each shadow Pokemon.
  * It costs nothing to leave enabled; it simply stops mattering per Pokemon
    once that Pokemon has been met.

The shadow definition table is at [r13 - 0x78B4] (US r13 = 0x80480820, so the
pointer is at 0x80478F6C; it read 0x808A7AC4 in the dump).  Entries are 0x38
bytes, bounds-checked to 0x60, with the species at +0x02, level at +0x08 and the
memo entry index at +0x0A.  Entry 1 is Makuhita (species 0x014F, level 30).


-------------------------------------------------------------------------------
USING IT
-------------------------------------------------------------------------------
Enable v2 together with codes/fix_shadow_shiny_glitch_US.txt and the anti-AR NOP
set, with Dolphin in JIT64 SC mode.

    this code (0x801FA3E8)   -> a shadow's PID is rolled shiny against YOU
    the glitch fix (0x80123FA8) -> the record carries YOUR OT SID/TID

Together the in-battle check computes OT_TID ^ OT_SID ^ PID_hi ^ PID_lo == 0 and
the Pokemon renders shiny while the enemy still owns it.

Do NOT also enable "Shiny Nation" / all-new-Pokemon-shiny: it hooks 0x801FA3E4,
the instruction immediately before this one, and forces every roll shiny, which
defeats the point of the gate.
